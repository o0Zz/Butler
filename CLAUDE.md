# Butler

Windows tray app that runs an agent CLI headless (Claude Code `claude -p` by default, or GitHub Copilot CLI) on triggers and shows what ran.
Single user, single machine: triggers live in the user's own skills folder and call their skills, mailbox and folders.

## Configuration
- Butler's own settings are local to the machine: `%LOCALAPPDATA%\Butler\settings.json` (`Settings`), edited on the dashboard's Settings page (also by hand; an unknown `cli` is refused). Today: `cli` (`claude` or `copilot`), `triggersFile`, `skillsFolder`, `adoOrganization`, `todo` (`none`, `todoist`, `txt`), `todoFile`; defaults when the file is missing: claude and `~/.claude/skills`. New options go there, with a field on the Settings page.
- Every Butler process reads the settings when it starts (runs are separate processes, so a change applies to the next run). The tray watches `settings.json` and the triggers file it points to, and reloads + syncs on change.
- Saving from the Settings page refuses invalid values (`Settings.Problems`: CLI not installed, missing file or folder) and shows them next to the fields.
- Secrets (the Todoist token) go in the Windows Credential Manager (`Secrets`, `Butler/Todoist`), never in `settings.json`. A new token is checked against Todoist before it is saved.

## To do page
- The to-do list the `todo` setting points to: `src/Butler/Todo/`, one `TodoBackend` per value (`Todoist`: API v1 with the user's token; `TodoTxt`: a todo.txt file, project = first `+tag`, a task's id is its line). Quick add, add at a place (the "+" between tasks: `Insert`), drag and drop by the grip, among siblings or to another list / section (on a task, a header or a list's chip; `Place` → `MoveTo` + `Reorder`; Todoist: `/move` then Sync API `item_reorder`; todo.txt: the first `+tag` changes), edit (drawer), complete with undo, delete. Lists can be hidden from "All" (`todoHidden` in the settings, project ids). Agents reach the same list through their own tools (Todoist connector, or the file).
- Loaded off the UI thread when the dashboard opens, every minute while open and after each edit. An edit never overwrites a change made meanwhile: todo.txt refuses when the task's line is no longer in the file; Todoist sends a date only when it changed (sending a recurring one back would reset it).

## How it works
- The triggers file (`triggersFile`, by default `~/.claude/skills/butler.json`) is the source of truth for triggers. It lives in the skills git repo, next to the skills it calls (not in this repo). `on` is the kind: `schedule` (`schedule`: `daily HH:mm`, `weekly:mon HH:mm`, `monthly:28 HH:mm`), `mail` (`from`: sender addresses), `ado` (`where`: a WIQL condition), `file` (`folder`, optional `filter`). Event prompts can use their kind's `${variables}` (filled by `Trigger.PromptWith`; without variables the event is appended; run by hand they stay unfilled with a note).
- Trigger kinds: `src/Butler/Triggers/`, one `TriggerKind` subclass per `on` value, listed in `TriggerKind.All`. A kind declares its fields (unknown ones are rejected; they land in `Trigger.Fields`, read with `Field`), its variables and the context appended to the prompt, a description for the dashboard, and for event kinds `Poll` + `Interval`. To add a kind: one class there, its tests, and its doc in the skills folder's CLAUDE.md. The tray polls event kinds on one STA thread (not the UI thread). A poll either completes or moves no checkpoint (`Checkpoint`, in `state/<kind>.json`); the first poll of a trigger starts from now.
- ado: `az boards query` on the `adoOrganization` setting, every 2 min, run through az's own `python.exe` (az.cmd goes through cmd.exe, which breaks the WIQL quoting). Variables `${id}`, `${title}`, `${state}`, `${by}`.
- file: new files in the folder (not subfolders), once unchanged for 10 s. Variables `${path}`, `${name}`. A new folder or filter starts from now.
- Teams is not a kind: az's Graph token has no chat scopes, so it needs an Entra app registration first.
- Schedule triggers: `TaskSync` reconciles the Task Scheduler folder `\Butler\` with the JSON (create / update / delete; a hash of schedule + exe path in the task description detects changes). Each task runs `Butler.exe run <name>`, which reads the prompt from the JSON at run time, so prompt edits need no sync. Tasks are "run only when user is logged on" (notifications and Chrome need the session) with "start when available" (catch-up).
- Mail triggers: the tray app polls every mail folder of the default Outlook classic mailbox through COM every 30 s (`OutlookInbox`; not only the Inbox, since rules move mails; Deleted, Outbox, Sent, Drafts and Junk are skipped), from a checkpoint in `state/mail.json` (`Checkpoint`), so mails received while Butler was closed are handled at the next start. First start begins at "now".
- Every run is a separate `Butler.exe` process (`run`, `answer`), never inside the tray process. The tray app only syncs, polls mail and displays files.
- The CLI is global, from the `cli` setting. `Cli` holds what differs (arguments, reading its JSON lines into text / tool / result events); a run records its `Cli`, and answers and "Continue in terminal" use that one. Copilot has no system prompt option (the protocol goes in the prompt), no final result event (the result is its last message), no cost, and needs `--allow-all-tools` (no classifier like claude's auto mode); claude-in-chrome is claude only.
- `Runner` starts (for claude) `claude -p --output-format stream-json --verbose --permission-mode auto --session-id <guid>` from the user profile folder (not this repo: this CLAUDE.md must not leak into triggered runs). It appends a protocol to the system prompt: end with `BUTLER-ASK: <question>` (run becomes Waiting) or `BUTLER-SUMMARY: <outcome>`. An answer resumes the same session with `--resume`. A run records its process (`Pid`) and claude's (`ClaudePid`): `Stop` kills claude's tree, and a Running run whose process is gone is marked Stopped when listed.
- Data in `%LOCALAPPDATA%\Butler`: `settings.json`, `runs/<id>.json` (record) + `runs/<id>.log` (raw stream), `state/` (mail checkpoint), `webview/` (WebView2 profile).
- Dashboard: `dashboard.html` (embedded, plain JS, `marked.min.js` inlined for Markdown) in a WebView2. C# pushes the whole state as JSON; the page posts commands back (`DashboardForm.OnCommand`). Claude output can quote mail content: raw HTML is escaped, only http(s) links are kept, and the WebView never navigates away (links open in the browser).
- Triggers tab: cards with the last 10 runs (dots), the cost over 30 days, and an editor (drawer) to add, edit and delete triggers. Its form comes from the kind's `Form` (field types `text`, `list`, `folder`, `schedule`), so a new kind needs no UI work. Saving reads the triggers file from disk, applies the change, validates everything (`Trigger.Save` writes nothing when a trigger is wrong) and writes it back in its usual layout and line endings (`Trigger.Save`); the tray then syncs.
- Sidebar "Watching": each event kind's last poll and its error (`TrayApp.Sources`), e.g. Outlook not running. Runs header: waiting, running, runs today, failures over 7 days, cost this month (from the last 1000 runs, read at most once a minute).
- "Ask AI" (Triggers tab) opens the interactive CLI in Windows Terminal in the skills folder, whose own CLAUDE.md explains butler.json: the agent edits the triggers, the watcher syncs and refreshes. No chat inside Butler.
- Skills tab: folders of the skills folder with a `SKILL.md` (front matter `name`, `description`), and which triggers call them (`/skill` at the start of the prompt).
- Notifications: `Microsoft.Toolkit.Uwp.Notifications` toasts; buttons call back through `Program.OnToast`, which starts `Butler.exe answer ...` or opens the dashboard.

## Commands
- `dotnet build`, `dotnet test` (from the repo root).
- Version: `X.Y.Z.<commit count>`, set by the csproj's `GitVersion` target (`VersionBase` 0.0.0; CI passes the tag's, so `v1.0.0` → 1.0.0.N). Shown under the dashboard's title with its commit (`Program.Version`).
- CI: `.github/workflows/ci.yml` builds and tests every push and PR on windows-latest; a `v*` tag also publishes `Butler-<version>.exe` to a GitHub release: one self-contained single file (native libraries extracted at start), so nothing in Butler may rely on files next to the exe.
- `Butler.exe` (tray), `Butler.exe run <trigger> [var=value ...]`, `Butler.exe answer <runId> <text>`, `Butler.exe sync`.
- `BUTLER_DATA` overrides the data folder (and so the settings). Use a scratch `BUTLER_DATA` for manual tests, with a `settings.json` pointing at a scratch triggers file.

## Rules
- Never touch Task Scheduler tasks outside `\Butler\`. Tests use a throwaway `ButlerTest-<guid>` folder and delete it.
- The tray app and `sync` always register tasks from the config they read: while testing, use a scratch `BUTLER_DATA` whose `settings.json` points at a triggers file without schedule triggers, or accept that the real ones get (re)registered.
- Outlook access is read-only. Never send, move or flag mails.
- Tests run against real things where possible: real Task Scheduler, real Outlook (skipped when not running), real Azure DevOps (skipped unless `BUTLER_TEST_ADO_ORG` is set to the organization URL), real folders, and a fake `claude.cmd` for the runner.
- Keep it small: tray in WinForms code, UI in the single `dashboard.html`, no front-end build, no extra layers.
